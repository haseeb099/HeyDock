## Choose a dull workflow, write the bounds, and allow yourself to stop

An AI pilot is a learning exercise, not a transformation announcement. The useful first project is often boring: a repetitive, well-understood workflow with clear inputs and a way to tell a good output from a bad one. If you cannot describe that, you are not ready to pilot; you are ready to wander.

Write a success check in advance. 'It feels impressive in a demo' is not a check. 'It drafts a first response that a reviewer accepts four times out of five, in a week of real tickets' is a check.

Write the bounds. Which data may be used, and for what? What must the system never do? Who reviews the output, and what happens when the system is unsure? The default should be that your data is not used to train a public model unless you have explicitly agreed that.

Keep a human responsible. Automation can remove repetition; it should not remove accountability.

Decide in advance how you will stop. A weak result is a valid outcome. Extending a poor pilot because someone has already announced it is how organisations collect tools nobody trusts.

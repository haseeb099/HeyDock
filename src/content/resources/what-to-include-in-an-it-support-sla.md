## Write the hours, the channel and the exceptions, or the document will not survive a busy week

An IT support SLA, or a simpler service description, is useful only if the people on both sides can operate it. The document should say how to raise work, which hours are covered, what a response means, and what is out of scope. It should not exist to decorate a proposal.

Start with hours. If you have bought a weekday service, write that down. If a small set of systems has an extended window, name those systems. Do not hide a hope of night cover in a footnote.

Then write the channel: email, portal, phone, or chat. A ticket that can arrive in six places with no record is not a process. Say who may raise a request, and what happens if a request arrives outside the agreed path.

Priorities need examples, not only numbers. 'The office card network is down' and 'a typo on a letterhead template' should not look the same. Response time is not fix time. If you cannot staff a fix-time, do not print one.

Out of scope is a kindness. Projects, new sites, hardware refresh, and third-party application defects should be listed as things that need a separate brief. So should any location you have not agreed to attend.

End with a review habit. A quarterly look at noisy tickets is more valuable than a clause nobody has read since signature.
